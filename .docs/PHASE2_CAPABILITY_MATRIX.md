# Phase 2 capability matrix: every service operation

Written for the owner and the developer. Generated by `node scripts/capability-matrix.js` from the service’s own operation registry and from `src/server/sync/operationKinds.js`, the table the cloud routes by, so the list, the permissions and the column “While the shop is reachable” are exactly what the program does. The design is in [PHASE2_ARCHITECTURE.md](PHASE2_ARCHITECTURE.md).

**161 operations, one behaviour.** Each has one definition and one permission, used by both ways in.

- **While the shop is reachable (implemented, milestone 1):** the cloud answers 79 itself (the reads, sign-in and sign-out), carries 71 to the shop where the operation’s own handler runs as the same user, and refuses 11 that belong to the shop PC.
- **While the shop is unreachable (milestone 3, not implemented yet):** the last column says what will happen, and the kind says how the two sides are brought together afterwards. Until then a change is refused with a clear message and nothing is queued.

| Kind                                                                      | Operations | On reconnection                                                                                        |
| ------------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------ |
| View                                                                      | 77         | –                                                                                                      |
| Adds up (sale, return, payment, purchase, movement, shift)                | 18         | Both sides’ records are kept and added; a broken limit is listed                                       |
| Merged by field (product, price, customer, supplier, user, role, setting) | 34         | Field by field; the same field changed on both sides keeps the shop’s value and is listed              |
| State of a record (close, approve, reject, cancel, complete, reverse)     | 12         | Taken as it is; if both sides changed the same record, the shop’s result stands and the case is listed |
| Needs the connection (barcode change, deleting a record, reset)           | 6          | Cannot happen apart                                                                                    |
| Per device (sessions, reservations, backup files, link)                   | 14         | Not synchronised                                                                                       |
